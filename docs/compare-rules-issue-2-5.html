先看结论

  1. 判断“有没有变化”用的是提取原文，逐个字符比较。标准化后的文字只用来找“旧的哪块对应新的哪块”，以及判断是不是只差格式（B 节）。
  2. 配对先看身份，再看原文，最后才看相似度。字段按“章节 / 主体 / 字段名”认；表格行按名称、编号这类非数值格认；金额、份额、日期只比较，不拿来认记录。表格行永远不按文字相似度配对（E 节）。
  3. 拿不准就公开：身份冲突、重复原文、工作量超限都会列进“需要核验的范围”，状态显示“未完全覆盖”，组内的原文变化照样出卡（H 节）。
  4. 所有卡片默认可见。分类只决定排序和筛选，不隐藏任何卡片（G、I 节）。
  5. 分类靠“角色 + 数字 + 关键词”的固定规则，不理解语义：页眉区、标题、标签的变化一律算形式变化；句子里只要有数字或 and/or，整张卡就算重要变化（G 节、M 节）。
  6. “比较完成”只表示程序在可提取文字范围内跑完、没有报告缺口，不表示每张卡都对。M 节里好几个错误结果都显示“比较完成”。
  7. #2 还有三条已复现的问题没修：只改某一页的页眉限额会被完全吞掉；页码和金额在同一行时金额变化被当成形式变化；列位置错开时两条不同记录被当成同一条（J 节）。

A

读取：哪些内容会进入比较

程序先用一个 PDF 引擎（PDF.js 或 MuPDF，二选一）把每页读成“字符 + 位置 + 来源”。读不到的内容不会被比较，而是作为“覆盖缺口”公开。

A1

只比较能提取出来的文字已实现

图片里的文字不识别（不做 OCR，即不从图片里认字）；批注和交互表单不比较。这些区域作为“覆盖缺口”列出，默认可见。

A2

覆盖缺口的六种原因已实现

整页只有图片（raster_only_content）、页内有图片区域（unverified_image_text_region）、有无法解码的字符（encoding_unknown，即出现替换符 �；MuPDF 还检查孤立的代理字符）、页面解析失败（page_failed）、批注或表单（unsupported_objects）、正文缺失（body_missing，数据格式里预留，目前两个引擎都不会产生）。每条带侧别、页码、区域、证据和提示语。

有缺口就是“未完全覆盖”，读到的文字照常比较已实现

D

页面附属：页码、页眉页脚、水印

页面附属指页码、页眉页脚里的合同号（UMR）、条码文字、水印这类每页重复的内容。#2 阶段 2 让它们“每条重复行只比较一次”，不再逐页出卡。

D3

逐页不同的数字必须“随页序走”已实现

同一组内文字逐页不同时，其中每一段数字要么各页相同，要么与页序同步加减（数值减页序保持不变）。满足的行标为“页码”；不满足的（例如每页不同的小计金额），这份文档自己不把它认作附属，仍按正文比较。但如果另一份文档在同一位置有同模式的附属，D4 仍会把它认作附属（J1 的原例就是这样被吞掉的）。各页文字完全相同的行是附属，但不是页码。

例实测反例：金额只在第 2 页由 1,000,000 变成 2,000,000 时，首段数字 1→2 恰好与页序同步，整行被标为“页码”（见 J2）。
