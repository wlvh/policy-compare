# 保单 PDF 比较：当前规则、问题证据与改进技术方案

日期：2026-10-28。文档状态：**技术评审稿，改进部分尚未实施**。

核查工作区提交：`de6e8d3ec6a5458a048e0c9299810719d5d8f4df`。产品实现仍与已接受开发基线 `1ce93d4dd41d1d46d5dd4b49a35f73d1b74a7183` 一致；已核对应用、引擎、公共核心、profile、补丁、基准和主要构建配置的差异为空。本次编写方案与读取诊断不代表重新执行完整功能或性能验收。

## 1. 结论与本方案范围

当前版本能读取 PDF 原文、保留来源位置、寻找新旧对应、生成变化并回到原文核对。PDF.js 与 MuPDF.js 共用核心和界面，各自独立构建。原 32 对规则与 F1—F7 修复的既有证据继续有效。

主要缺口出现在**把页面上的文字组织成段落、表格、记录**这一步。当前实现过度依赖固定表头、标签和位置阈值；结构判断错误会继续影响对应、分类和提示。两对新续保样本已证明：文字和位置读到了，仍可能无法完整表达“哪家公司发生了什么变化”。

建议优先补强公共的版面与表格处理：**先恢复行列和上下文，再寻找同一条记录，最后比较内容。业务规则用于解释变化，不再成为认出普通表格的前提。** 不以不断新增客户模板、降低匹配阈值或取消黄色提示作为主要方案。

保留当前原文契约、双引擎、比较核心中可复用的差异算法、UI 和评分器。此次不提出重建项目、改语言、引入第三个产品 PDF 引擎或默认上传文档。OCR、电子签名验证、任意复杂图形语义不纳入这一轮文字结构改进。

文中标签含义：

- **已实现**：直接来自当前源码；不等于在所有文档上已验证正确。
- **已确认问题**：有实际输入、输出或结构诊断证据。
- **待验证风险**：源码显示可能出错，但本轮没有形成独立反例或完整验收结论。
- **建议**：待实现并检验的设计，不写成现有能力。

## 2. 当前版本怎样完成一次比较

```text
用户选择旧 PDF 与新 PDF（同一引擎）
    ↓
读取文字、页面位置与解析诊断
    ↓
统一为 DocInput：原文、字符/提取项来源、页面与覆盖问题
    ↓
整理为标题、字段、正文、已知表格的单元格
    ↓
寻找新旧内容的对应关系
    ↓
对对应内容的原文计算增删，并识别移动
    ↓
给变化分类，汇总未比较或未可靠对应的范围
    ↓
显示卡片、左右原文高亮、待核验提示；允许导出 JSON
```

这里有三个容易混淆的动作：

| 动作 | 大白话 | 本项目中的对象 |
|---|---|---|
| 提取 | 读出“HPX 0624”“12.5%”以及它们在页面上的位置 | `DocInput` |
| 结构整理 | 确定这两个片段属于同一行，分别是承保人和份额 | `Unit`、结构路径 |
| 对应 | 确定旧版 HPX 这一行对应新版 HPX 那一行 | 配对结果、匹配依据 |

提取成功不保证结构正确；结构正确也不自动证明新旧对应正确。最终的变化必须同时保留旧、新来源，不能只凭数字在某处出现就认定检出。

### 2.1 入口、运行方式与范围

| 项目 | 当前规则 |
|---|---|
| 浏览器 | React/TypeScript；PDF 在本地浏览器处理，静态服务不提供上传接口 |
| CLI | 读取本地两个 PDF，调用同一适配接口与公共比较核心；显式 `--engine pdfjs` 或 `mupdf` |
| 输入限额 | 每份 1—100 页、最多 30 MiB、50 万提取 Unicode 标量；密码在本地提供 |
| 引擎隔离 | 两个独立构建；一次比较双方的提取器名称、版本及选项必须一致，无静默引擎回退 |
| 后台执行 | 提取/渲染与核心计算分离；逐页传递输入，两份提取均结束后核心开始比较，不是逐页提前宣布全量结果 |
| 生命周期 | 新任务使用新的任务标识；检查过期消息，取消/关闭时终止执行单元并释放资源 |
| 比较范围 | 可提取文字；图像无 OCR，批注/表单及无法可靠解码的内容有覆盖提示 |

入口和职责见 [适配接口](../packages/pdf-adapter/api.ts)、[PDF 执行单元](../apps/web/pdf.worker.ts)、[核心 Worker](../apps/web/core.worker.ts)、[CLI](../packages/cli/run.ts)。

### 2.2 两个引擎提供什么

| 项目 | PDF.js 路线 | MuPDF.js 路线 |
|---|---|---|
| 当前版本 | `pdfjs/6.4.299+strict-streams.1`，适配器 2 | `mupdf/1.28.1+scalar-fix.1`，适配器 3 |
| 原文来源 | 提取项，以及项内 Unicode 标量与 UTF-16 范围 | 原生字符及其来源 |
| 核心中的位置 | 提取项区域，标明 `run` 精度；没有均分宽度伪造字符坐标 | 原生字符四边形，保留其方向与精度 |
| 浏览器精细位置 | 使用同源文字层，核对项 ID、全文与偏移，再测量 DOM Range | 使用原生字符几何 |
| 严重解析错误 | `stopAtErrors` 与锁定 worker 补丁联用，传入页面/任务错误结果 | 在同步原生操作期间收集严重诊断，关联到当前文档/页面 |
| 图像覆盖 | 遍历图片绘制操作，组合 Form 矩阵与图形状态 | 使用引擎返回的图像区域 |

`disableNormalization: true` 已显式使用，但它不是“任何 PDF 都无损提取”的保证。原文指引擎提取原文，不能反向保证恢复错误字体编码背后的视觉文字。图片覆盖框是“尚未比较的区域”，不能当作词级高亮。

两版的 `DocInput`、来源 ID、卡片数或结果 JSON 不要求相同；它们分别满足相同业务事件与证据要求。相同冻结输入进入同一公共核心时，应可复现规范结果。详见 [来源契约](contracts.md) 与 [引擎能力](extractor-capabilities.md)。

`DocInput.lines` 也不自动等于人眼看到的一整行：PDF.js 当前逐提取项建立 line，MuPDF 使用其结构化文字行；表格中同一水平线上的多个单元格仍可能是多个 line。公共版面层需要按来源与坐标重新组织，不能把一个 line ID 直接当成完整表格行或自然段。

## 3. 当前比较规则：按实际执行次序说明

### 3.1 文字保留与用于寻找对应的标准化

程序同时保存两种文字：`rawText` 是提取原文；`matchText` 是帮助寻找对应的标准化文字。

`matchText` 做 Unicode NFKC 规范化，并合并连续空白，同时保存每个标准化位置回到原文的映射。最终增删仍使用 `rawText`，因此不能把“标准化后相同”当作原文没有变化。当前标准化不会笼统删除所有标点或忽略全部大小写。

分词将字母/组合字符、带小数点或逗号的数字、其他非空白符号分开。来源区间采用 Unicode 标量，浏览器文字层另转换为 UTF-16 偏移。结构整理结束会检查每个输入字符有且只有一个主要归属；逻辑分隔仍保留来源，不作为业务单词配对。

实现：[text.ts](../packages/compare-core/text.ts)、[contracts/index.ts](../packages/contracts/index.ts)。

### 3.2 结构整理：当前最主要的局限

以下是源码中的实际启发式规则，即依靠固定条件做出的近似判断：

| 内容 | 当前规则 | 实际限制 |
|---|---|---|
| 声明过的表格 | 连续提取行的文字必须依次等于 `REGISTRATION / SERIAL / MODEL / CCY / AGREED VALUE` | 只声明了这一种表结构；换列名、列数或提取拆分方式就可能不命中 |
| 显式章节 | 全大写标题形态且以 `SECTION` 或 `CHAPTER` 开头时，优先保留章节归属；紧随其后的大纲编号（如 `SECTION 10.1`）不计入“数字占比高即为代码”的判断 | 并非通用章节层级恢复 |
| 业务字段 | 按 profile 中的标签前缀识别，例如 `INSURED:`、`PERIOD:`、`DEDUCTIBLE:`；长标签优先 | 大小写、冒号、换行和同义标签不自动泛化；标签表见 profile |
| 主体 | `INSURED:` 与 `REINSURED:` 可区分主体，主体约束主要用于姓名、地址 | 没有自动识别任意公司记录的通用机制 |
| 页眉 | 字符原点纵坐标小于 110 pt | 使用绝对页面位置，没有通用的重复页眉学习 |
| 页脚 | 字符原点在距页底 50 pt 范围内；同基线页脚片段可拼接 | 较高页脚、封面例外等可能不命中 |
| 普通标题 | 全大写字母/数字及限定标点组成，长度小于 100 | 公司代码、参考编号、部分日期可能被当作标题 |
| 已知表格的一行 | 连续五个提取行在同页、纵坐标差小于 2 pt | 列数固定；仅在前面已经进入该表格状态时生效 |
| 字段/正文合并 | 字段后的内容按横坐标等条件追加；正文按当前标题状态追加 | 没有完整的通用分栏、段落间距、换行单元格判断 |

字段身份主要由“章节／主体／字段”组成。已知表格使用注册号、序列号作为两类行识别依据。**没有命中已知表头的内容仍可进入文字比较，但不会自动得到可靠的表格行归属。**

规则来自 [structure.ts](../packages/compare-core/structure.ts) 与 [aviation.ts](../profiles/aviation.ts)。这些条件是当前实现细节，不是对 PDF 文档的普遍事实，也不应成为要求用户定制每一种表格的产品规则。

### 3.3 新旧内容怎样配对

| 次序 | 当前做法 | 不确定时的行为 |
|---|---|---|
| 1 | 对已经识别的表格，优先使用两边唯一的注册号或序列号，对应后按列比较 | 主次键冲突、重复或剩余行不能可靠对应时，保留分列原文组和未决诊断；一侧独有内容另保留增删 |
| 2 | 唯一字段身份直接对应 | 重复字段先用稳定、唯一的标题进一步区分；仍不明确时仅在冲突组内比较原文并提示归属未定 |
| 3 | 唯一的完全相同原文直接对应；重复标题/页眉角色可聚合；重复正文尝试相同章节和标题 | 同样文字不自动等于同一业务对象 |
| 4 | 检查一个正文单元与相邻两个单元是否原文完全相同，处理拆分/合并 | 不任意跨越不同标题或章节拼接目标单元 |
| 5 | 用已知对应划出顺序窗口，在窗口内共同尝试一对一、一对二、二对一和增删 | 标题/章节必须一致；过大的窗口跳过这一步 |
| 6 | 对剩余候选计算文字相似度，按分数和稳定顺序选择；有并列竞争时不锁定 | 受角色、身份、上下文、长度与工作量预算限制 |
| 7 | 剩余正文中，标准化文字相同的片段进入待核验组 | 这些片段不再直接作为独立增删；不相关的剩余明确增删继续输出 |

相似度的含义是“保序保留下来的共同词，占两边总词数多少”，不是业务语义理解，也不是正确概率：

```text
相似度 = 2 × 最长公共词序列长度 /（旧词数 + 新词数）
同章节且同标题：门槛 0.60
跨上下文：门槛 0.95，且双方较短文本至少 8 个 token
局部联合窗口：旧单元数 × 新单元数不超过 4096
```

最长公共序列（LCS）只要求词的相对先后顺序一致，不要求相邻。程序先用长度和词频交集排除明显不可能达到门槛的候选，再做较贵的 LCS。

当前模糊对应预算为最多 20,000 个已计分候选、累计 token 长度乘积不超过 100,000,000。预算是计算工作量限制，不是耗时承诺；确定字段身份的直接对应不靠放宽这个预算实现。源码：[配对与评分](../packages/compare-core/index.ts)、[顺序对应算法](../packages/compare-core/alignment.ts)。

### 3.4 差异、移动与重要性分类

确定对应后，精细增删以 Unicode 标量计算：先剔除相同前后缀，再做标量 LCS，合并连续 equal/delete/insert，并关联回来源。界面常称“词级高亮”，但当前差异算法本身不是只按整词比较。剩余长度乘积超过 4,000,000 时，保留双方原文并提示精细差异预算不足。

变化操作和重要性是两个独立维度：

| 维度 | 当前含义 |
|---|---|
| Added / Removed / Replaced | 新增、删除、双方有对应后的文字修改 |
| Moved | 正文发生章节或相对顺序变化；使用保序对应作为稳定参照，不单凭页码变化判移动 |
| Material | 重要变化；由字段、数字、部分符号/词等规则触发，不是完整保险语义裁决 |
| Review | 待复核；对应不可靠或普通文字变化不能由当前规则归类 |
| RollForward | 保期顺延；识别为保期字段、符合指定英文日期格式、连续年度区间，且非日期原文完全不变 |
| Cosmetic | 格式性；由标签/表头角色、匹配标准化后相同的原文、已确认的页码部分，或有重分页证据的标题决定 |

`category()` 的执行顺序很重要：先看标签、表头等格式角色，再看标准化相同、保期顺延、归属未定和重要词/数字。**误判为标签后，不能指望后面的数字规则自动纠正重要性。** 没有完整的同义词、否定语义或任意日期格式理解。

（issue #2 第三、四轮复核后更新）标题、页眉、页脚不再因角色本身归为 Cosmetic：只有去掉显式“Page n”页码后原文相同、单侧只含页码，或续页标题（“… CONTINUED” 且基础标题两版都有）才是 Cosmetic；其余按正文规则归为 Material 或 Review。第三轮曾对“页数不同、两版每页同一位置都有页标题时新增页上的无数字标题”豁免，第四轮因没有正面证据（同样会隐藏 `WAR EXCLUSION`、`POLICY CANCELLED`）而取消，R16 的 `POLICY WORDING` 因此为 Review。

原文完全相同但判定移动的正文，目前默认归 Review。所有变化默认可见，分类用于排序/筛选，不授权删除低优先级原文。当前排序为 Material、Review、RollForward、Cosmetic，再按来源位置与稳定 ID 排序。

### 3.5 完整性、高亮与用户界面

结果分三部分保存，不能只看差异列表：

| 字段 | 意义 | 例子 |
|---|---|---|
| `differences` | 已产生的变化及对应依据 | 某段免赔额修改 |
| `coverage` | 提取或支持范围的缺口 | 图片文字没做 OCR、编码未知、页面解析失败 |
| `unresolved` | 文字已经读到，但对应或精细比较尚未完成 | 重复字段归属未定、对应工作量用尽 |

只要存在 coverage 或 unresolved，核心就把结果标为 partial。complete_for_scope 仅表示算法在声明范围内结束且未报告这两类缺口，不是“任意业务变化均已正确识别”的证明。运行中的失败、取消由外层分别处理。CLI 完整/partial/失败/取消退出码分别为 0/2/3/130；存在正常差异不导致失败退出码。

点击差异优先使用变化片段的来源高亮；PDF.js 显示时测量真实文字层范围，MuPDF 使用原生几何。搜索是原文查找，不是差异卡片筛选。同步滚动参考保持顺序的对应点；移动关系和滚动关系分开。

待核验按钮当前只展示统一 message，点击后跳到每侧第一个位置。组内其余位置可能在别页，缺少逐处导航与明确的核对完成记录。这是可操作性局限，不能由“按钮可点击”推出“整组容易核对”。实现见 [main.tsx](../apps/web/main.tsx) 与 [PageCanvas.tsx](../apps/web/PageCanvas.tsx)。

## 5. 新问题、证据与根因

### 5.1 RENEWAL-02：承保人和份额没有形成一条记录

**已确认，两引擎都存在。** 航空样本 PDF 第 8 页：HPX 0624 的份额从 12.5% 变为 10.0%。当前输出只有旧 12.5% 的删除卡片，新 10.0% 的来源留在重复百分比待核验组，没有形成完整的“HPX：12.5%→10.0%”业务事件。状态为 partial，因此这里是有警告的结果不完整，不称为完整零差异或完全静默漏报。

两引擎实际提取的位置如下：

| 同一旧版行中的内容 | 横坐标 | 纵坐标 | 当前结构结果 |
|---|---:|---:|---|
| HPX 0624 | 66 | 345.9 | 标题；主体、表格和行标识为空 |
| HX-AV-2210 | 256 | 345.9 | 又一个标题 |
| 12.5% | 371 | 345.9 | 上一编号标题下的正文 |
| 03/10/2024 | 467.06 | 345.9 | 提取位置与上述内容同一行 |

根因链：提取成功 → `Insurer / Reference / Written Line / Stamp Date` 未命中固定表头 → 同一行没有组织成记录 → 大写公司代码和编号误当标题 → 百分比成为孤立正文 → 新版重复 10.0% 无可靠归属。

这张表具备支持正确对应的信息，主要问题在结构整理。只换 PDF 引擎、降低文字相似度门槛或取消 partial，不能解决这条根因链。

证据：[结构诊断](../reports/renewal-intake/structural-diagnostics.json)、[事件与精确来源检查](../reports/renewal-intake/findings.json)。2026-10-28 另用既有只读诊断脚本重跑了两引擎、左右文档，共四条记录；未修改产品。

### 5.2 RENEWAL-01：页码被判成重要正文变化

**已确认，两引擎各 35 张纯页码卡片为 Material。** 商务航空样本中的 `Page 1 of 17` 删除和 `Page 1 of 18` 新增是例子。

证据：[findings.json](../reports/renewal-intake/findings.json)。作者 H4 将页码记为 Header；原页面已核对。应保留页码变化的原文证据，但不作为独立重要业务变化淹没清单。

### 5.3 待核验提示缺乏足够上下文

**已确认的实现和可操作性局限。** 航空样本 PDF.js 有 227 张卡片、13 组待核验；MuPDF 为 226/13。商务航空两版均为 400/2。四个结果都是 partial，coverage 均为空。

应把“算法没有确定对应”“确实有多个同样候选”“提取缺口”“精细位置不足”分开描述。黄色提示是风险披露，不是归属恢复能力的替代品。

## 6. 可选解决路径及建议

| 路径 | 做法 | 收益 | 成本与边界 | 建议 |
|---|---|---|---|---|
| A. 继续增加模板规则 | 为 Written Lines 等表逐个增加表头、列数与专门行键 | 对当前一张表较快见效 | 新模板继续失效；容易围绕已知答案开发；无法解决普通文字与表格混淆 | 只作为明确业务配置或兼容措施，不作为主要架构 |
| B. 公共版面恢复 + 通用行列对应 | 从既有坐标、方向、间距等恢复结构；以整行多项证据对应 | 保留现有引擎和本地架构，处理未知列名；解释与复现较直接 | 要处理换行、跨页、表格与双栏正文区分；通用性必须实测 | **推荐首选** |
| C. B 加本地版面模型辅助 | 模型建议表格区域或行列，再由原文来源与结构约束核验 | 可能帮助规则信号弱的复杂版面 | 引入模型体积、推理运行时、维护和内存成本；当前无实测可行性 | B 的盲测出现明确瓶颈后，小范围验证 |
| D. 仅靠相似度/状态文案修补 | 放宽短文本门槛、强配相同金额、取消黄色提示 | 表面上减少未决或卡片 | 可能重现跨主体值互换漏报，或把未完成包装成完整 | 不采纳 |

路径 B 的“通用”是**同一算法能够处理声明范围内、没有事先写入表头名单的表格**，不是保证识别任意 PDF。需要提前声明支持范围，并用未见过的模板验证；达不到时如实展示具体范围，不能暗中缩小输入范围来宣布通过。

参考实现仅用于评估思路：pdfplumber 的 `words_to_edges_h/v` 根据文字顶部、左右边界或中心对齐推导候选边界，`get_edges` 可结合线条和文字策略；本次阅读了对应源码。这支持“先用几何恢复结构”的可行方向，不证明本项目已经实现，也不意味着将 Python PDF 解析器加入产品。[pdfplumber 表格源码](https://github.com/jsvine/pdfplumber/blob/stable/pdfplumber/table.py)

模型路径也不是直接理解保单：Table Transformer 的官方实现从图像预测表格、行、列等对象，文字需另行提供；推理代码有 PyTorch 等依赖，不能直接当作已适配浏览器的模块。官方仓库在本次核查时已归档，仅作为研究参考。本项目没有测量其中文/保单泛化、速度、内存或部署可用性。[官方说明](https://github.com/microsoft/table-transformer)、[推理源码](https://github.com/microsoft/table-transformer/blob/main/src/inference.py)

## 7. 推荐方案的具体设计

### 7.1 增加“原文事实之上的结构解释层”

DocInput 继续保存事实：引擎读到了什么、位于哪里、从何而来。新增内部 `LayoutDocument` 保存解释：哪些片段是一行、一个单元格、一张表、一个段落；解释有依据，也可能未确定。

```text
冻结 DocInput（原文与来源不改写）
    ↓
公共版面恢复（区域、行列、段落、页面附属内容）
    ↓
LayoutDocument（结构解释、来源引用、未决原因）
    ↓
区域/表格对应 → 列对应 → 行对应 → 单元格原文差异
    ↓
业务分类 + 可操作的原文核对
```

以下是概念数据，不是已新增接口：

```text
表格：所属章节、页面区域、列、行、跨页关系、识别依据
行：各单元格、可能的记录识别信息、是否存在竞争候选
单元格：原文来源引用、行/列跨度、换行片段
未决项：具体范围、原因、候选关系、缺少的证据
```

每个字符仍有且只有一个主要内容归属；其他结构是引用，不复制或丢弃原文。连字、标量/UTF-16、native quad 与文字层范围继续使用原契约。虚拟拼接空白必须可区分于提取字符，不能编造来源坐标。

内部层优先独立于 DocInput，减少破坏已有提取与快照。若为线条/矩形辅助扩展输入，必须让两个适配器显式声明能力和来源，版本化 schema 与快照。当前 DocInput 没有通用表格线条集合，不能在方案实现中假定已经可用。

### 7.2 通用区域、行、列与段落恢复

1. **先局部分区，再归行。** 按页面方向、文字范围和空白分隔识别候选区域；禁止把整页相同纵坐标的两栏正文直接拼成一行。
2. **使用相对尺度。** 归行/换行容差参考当地字号、字高和行距，避免把 110 pt、2 pt、120 pt 当作所有模板的普遍规则。
3. **寻找稳定列分隔。** 利用多行重复的横向对齐、空白间隔和内容分布。列名可帮助解释，但未知列名也能形成列。
4. **识别真正的数据行。** 将同一区域内的单元格组合，允许一个单元格换行、空单元格和不同列宽；表格内的大写代码不再直接进入正文标题判断。
5. **处理表格外正文。** 使用局部行距、缩进、标点和阅读顺序组织段落。对无法确定的区域保留原文组和待核验关系。
6. **谨慎处理跨页。** 重复表头、列位置、所属章节和边界行共同支持续表；页码不同不等于记录移动。合并单元格、跨页断行证据不足时局部未决。

第一阶段优先使用现有文字坐标。需要边框线作为补充时，从当前选定 PDF 引擎取得绘制信息并统一坐标；不增加第三个产品 PDF 引擎。不依赖 PDF.js 伪造的字符宽度，也不要求它与 MuPDF 的提取项完全一致。

如果 PDF.js 的一个提取项跨越多列，项内字符共享的 run 区域不能用来假装已经知道各字属于哪个单元格。应保留原项/来源范围并标记结构不确定，或使用额外可验证的分列依据；不得均分宽度造坐标。浏览器的文字层精细测量继续负责定位，不偷偷改变同一冻结输入下的核心对应结论；未来若将测量作为结构输入，须明确冻结、版本化并分别验证 CLI 与浏览器契约。

版面识别应先给出候选及可检查依据，例如“连续七行在四列位置稳定对齐”；未经校准，不把自定 0.99 分数写成 99% 正确概率。

### 7.3 新旧表格、列和记录的对应

先确定可比较的表格范围，再比较行。所属章节、表头组合、列形状与上下文用于排除不相关表格；相同数字不能跨表格或跨主体直接配对。

列对应允许顺序调整、增删和名称变化。先使用清楚的表头及数据类型证据；不明确时保留列级未决，不默认为“第 3 列永远对应第 3 列”。

行对应的原则：

- 在表格范围内寻找两边唯一、相对稳定的名称或标识；必要时使用多个单元格组成的识别信息。
- 数字可能是序列号，也可能是待比较金额。不能简单禁用所有数字，也不能把份额/金额相等作为唯一身份依据。
- 候选只在合理范围内生成。对冲突候选考虑整组的一对一分配；保留最佳候选、竞争候选与拒绝理由，避免贪心锁定导致后续错配。
- 同一名称重复且无法区分时，只将有关行放入局部待核验；独立明确的新增/删除继续生成完整业务事件。
- 身份字段自身变化时，其他稳定列和局部结构可以提供证据；证据不足就保留双方记录，不编造归属。

```text
对每对可靠对应的表格：
    对应列
    为各行生成有依据的候选身份
    先绑定双方唯一且无冲突的记录
    对局部竞争组共同决定对应或保留未决
    对可靠对应行逐单元格比较原文
    对确定独有行报告新增/删除
    对未决组保留全文、数字变化线索和双方位置
```

HPX 的验收结果应明确归属到 `HPX 0624`，包含 `12.5% → 10.0%` 和双方份额来源。SLD 退出、Corvane 新增、Nordvik 份额不变须分别成立。不能通过同百分比配对、吞掉新增/删除或把全表设为 partial 来绕过这些断言。

### 7.4 页眉、页脚、水印与重要性规则

页面附属内容应由多种证据识别：位置在页面中的比例、跨页重复、页码递增形式、字号/方向以及是否进入表格或正文。封面允许有不同样式，纯位置不能授权删除内容。

对于已确认的页码和重复水印，建议展示格式变化组并保留全部出现位置、计数和展开入口。明确的保额、条件或正文变化即使出现在页面上方，也不能因为“像页眉”就消失或无条件变成 Cosmetic。

分类应分开考虑：原文是否变化、身份是否可靠、业务重要性依据。显示区域角色仅是证据之一；不能用误判的 heading 抢先覆盖所有内容判断。保期顺延仍要求非日期内容不变，日期解析扩展需有独立用例，不能顺带掩盖 includes/excludes 等修改。

### 7.5 将待核验变成明确、可处理的工作项

建议状态文案把“计算是否结束”和“结果哪些部分未确认”分开。保留现有顶层 partial 兼容性，增加结构化的原因与范围；具体新增字段需在实施时版本化。

示例为拟议文案，不代表现在的界面已经如此显示：

```text
比较已结束；另有 2 组对应关系需要核验。

承保份额表 · 旧第 8 页 / 新第 8 页
原因：旧版有 2 处、新版有 3 处相同的 10.0%，所属记录未确定。
查看整组：显示承保人、编号、份额及所有出现位置。
```

每组应显示对象/章节、双侧页码、出现次数、具体原因和所有位置的导航。允许人工记录确认，但人工确认独立保存，不能悄悄改写原始算法结果。分开统计“已列变化”“身份未定”“提取缺口”和“精细定位不足”，不把它们相加生成貌似精确的覆盖率。

### 7.6 代码落点、确定性与性能控制

| 模块 | 建议改动 |
|---|---|
| `packages/compare-core/layout/`（拟新增） | 区域、行列、段落、页面附属内容恢复；只依赖冻结输入 |
| `structure.ts` | 接收结构解释；保留来源和字段含义；逐步替换固定表头作为必要入口的逻辑 |
| `index.ts` / 配对辅助模块 | 在可靠区域内对应表格、列和行；保持局部歧义、原文增删与预算行为 |
| `profiles/aviation.ts` | 只提供业务含义、可选标签/键提示和策略，不枚举每个客户模板 |
| `contracts/index.ts` | 必要的结构依据、未决原因、版本与来源引用；不降低精度要求 |
| `apps/web/` | 对应依据、整组核验与逐处导航；保留现有双栏与全量变化入口 |
| `tests/evaluation/` | 独立业务事件评分和失败反例；不读取产品结果生成答案 |

相同输入、配置和工作量预算必须产生稳定结果。布局/匹配算法增加版本标识，稳定排序与平局规则不能依赖时钟；来源 ID 不用随机数。新增结构缓存只在单次任务内使用；切换引擎或输入必须重新提取与比较。

先按页、区域、列和候选标识建立索引，再做局部比较；避免把全部行对全部行计算。新增布局和行分配预算需明确记录、支持取消、保留未完成范围，不能靠提前返回 partial 达到原时间预算。既有基准中快照和验证也占较多时间，不能把所有成本归咎于 PDF 引擎或仅凭核心毫秒数决定优化方向。

## 8. 验收设计：怎样证明改的是通用能力

### 8.1 必须保住的既有结果

- 原 32 对与六个控制用例、全部原 expected/source/layout 保持不变，两版分别评分。
- F1—F7 回归继续通过，尤其归属下金额互换、坏页不假完整、局部歧义不压掉独立增删、日期混改和双侧精细位置。
- R18 连字、R21 勾选状态、R25 金额与双侧来源、R27/R28 图片覆盖继续保留要求。
- 同一冻结输入可复现；产品不读作者答案；PDF.js 仍可在没有 MuPDF 安装、下载、资源和请求的环境中运行。

### 8.2 新续保样本：逐事件而非数卡片

先保存修复前输入/输出/来源哈希与作者清单，再形成独立的事件核对表。每项分别检查发现、正确记录归属、完整变化、双方定位、默认可见性与完成状态。

作者清单 177 项正文和 5 项页面附属内容须逐项有结论，不能只抽查 HPX。作者的操作/分类或 `expect` 若沿用不同旧规则，应记录冲突并在实施前确认本项目验收解释；原 JSON 不变，未决项不能默认为 PASS。尤其要区分“页码不成为正文重要差异”和“把页码原文彻底删除”。

最小明确断言：

| 场景 | 必须得到的证据 |
|---|---|
| HPX 份额修改 | 12.5%→10.0%，归属 HPX，双方正确单元格；新版份额不能只在泛化待核验组 |
| 承保人退出/加入 | SLD 与 Corvane 分别删除/新增；不得被相同 10.0% 抵消 |
| 不变承保人 | Nordvik 的 10.0% 不产生错误份额变化 |
| 页码变化 | 不再产生 35 张 Material 页码卡片；原文证据与出现次数仍可查 |
| 重复页眉中的真实金额 | 业务变化仍保留，不能用去页眉修复页码后引入漏报 |
| 定位反向检验 | 只损坏任一侧最终高亮即失败；不以正确来源文本替代最终坐标检查 |

### 8.3 未见模板与受控变形

开发前冻结覆盖矩阵和作者预期。至少覆盖：未知列名、换列顺序、不同列数、有/无边框、公司名换行、不同字号/列宽、跨页重复表头、跨页断行、记录重排、同金额不同公司、同名不同编号、空格/合并单元格、双栏正文与“像表格的列表”。

受控变形分别检查两件事：仅改字号/换页/列宽时，业务事件不应改变；仅交换不同主体的金额时，应检出正确归属的变化。这些变形是补充回归，不冒充独立真实留出。换随机 seed 不等于换来源。

另用不同模板或生成来源、开发前未查看的样本，由独立审阅者先保存预期再运行。发现失败并用于修复后，该样本转为回归，补换留出。通用层不允许依赖这些样本的公司名、固定数值、文件哈希或案例编号。

### 8.4 浏览器性能与业务试用继续独立

核心或适配器变化后的正式结果绑定新 SHA，旧报告保留。两版仍使用同提交、同原始 PDF 字节、同 profile/预算、设备/浏览器/尺度/可见范围；三类长文档、每引擎每工作负载至少 20 次热运行，平衡 A/B、B/A，每轮重新读取、打开、提取和比较。冷启动另记，分项增加布局与行对应耗时。

原预算继续有效：小型热运行 p95 ≤3 秒；标准 ≤20 秒；交互响应 p95 目标 100 ms；取消目标 1 秒；标准相关进程/Worker/WASM/位图可归因峰值目标 ≤1 GiB。100 页容量组使用事先声明的完成/降级合同。错误、漏检、错误完整状态、错误定位或标准组提前降级不得算性能通过，成功耗时必须同时列成功数/总数。

完整内存与普通/实际目标设备仍须补证，JS heap 不代表完整内存。高配开发机或云端 Linux CI 不替代目标设备验收；不能用未校准的推断声称新布局处理必定达标。[原预算及测量口径](engine-comparison.md)

真实试用保持原安排：3—5 对获准真实文档完整人工审阅，另留至少 3 对不同来源的未调参样本。分别记录“程序有没有检出”和“人是否有效注意到”，观察误报负担与覆盖提示理解。缺少真实资料时完成独立工程工作，业务试点继续标明未完成。

## 9. 建议实施顺序与结束条件

| 里程碑 | 产出 | 进入下一步的条件 |
|---|---|---|
| 1. 冻结证据与评价 | 新资料作者事件核对表、现有失败、模板覆盖矩阵、结果/版本清单 | 原答案保持原样；预期冲突明确记录；不把流程 PASS 当产品 PASS |
| 2. 公共结构原型 | 不依赖特定表头的区域、行列与段落层，结构诊断视图 | HPX 行恢复、未知列名、双栏反例、换行和字符守恒验证；两版分别成立 |
| 3. 对应与分类接入 | 表格/列/行对应、局部歧义、页面附属内容处理 | 主体份额交换不消失，独立增删保留，页码降噪不伤业务内容 |
| 4. 核验界面与功能复验 | 具体原因、所有位置导航、完整作者事件报告、原规则和 F1—F7 回归 | 未知范围明确、全部必要断言逐项有结论，双侧来源与精细位置通过 |
| 5. 性能与目标试用 | 新 SHA 的公平 A/B、Linux/独立构建、目标设备和真实审阅报告 | 工程与业务分别按原条件判断；未满足项继续明确保留 |

每个里程碑保留可运行提交和报告，不覆盖原失败或旧测量。开发期间可以用同一输入并排比较旧/新结构输出，但默认产品不长期保留两套正式比较算法。完成验证后由新公共层接替旧固定入口；发生回归时回到已保存的产品版本，不回滚或改写用户工作。

本方案不以“黄色数量归零”“卡片减少”作为结束条件。结束条件是：声明支持范围内的重要变化被完整、正确地对应并可定位；无法解决的范围具体可查；原回归、性能和部署条件分别得到真实证据。
