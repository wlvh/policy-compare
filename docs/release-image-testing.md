# 候选发布镜像测试流程

本流程在本机 Docker 中运行准备部署到 OpenShift 的同一候选镜像，供发布前人工检查。无需 Red Hat 账号或 OpenShift 集群；不启动开发服务器，不从当前源码重新打包。

发布检查顺序为：**候选镜像构建与自动检查 → 同镜像人工试用及记录 → OpenShift 测试环境验证 → 正式环境推广与指定使用者验收。** 每一阶段单独记录结果。镜像试用通过后，OpenShift 的网址接入、权限、网络策略和升级回滚仍需在实际集群验证。

GitHub CI 的两引擎 Linux 容器任务会在候选检查成功后，再执行同镜像体验入口检查，验证启动与版本一致，并确认人工项仍为未评价。CI 结束前清理专用容器、上传记录；实际人工试用按以下步骤另行执行。

## 第 1 步：准备候选检查记录

**执行位置：**macOS/Linux 终端，仓库根目录；使用 Node.js 24、pnpm 10.12.1，Docker 服务已启动，根目录依赖已安装。

源码统一从 `main` 获取，相关 PR 合入后执行。候选镜像应已按 [OpenShift 部署指南第 6 步](deployment.md#第-6-步打包并自动检查候选镜像)完成构建和自动检查。本流程也可复用之前保留的候选镜像，不要求已有集群配置。

将候选记录路径写入变量。下方是上一轮候选的实际路径；检查其他版本时，替换为该版本的 `container.json`：

```sh
export POLICY_CANDIDATE_REPORT="$PWD/reports/local-deploy/r20261104-bc9105e-mupdf/container.json"
node -e 'const fs=require("node:fs"); const c=JSON.parse(fs.readFileSync(process.env.POLICY_CANDIDATE_REPORT,"utf8")); if(c.status!=="PASS")throw new Error("候选自动检查未通过"); console.log(JSON.stringify({releaseId:c.releaseId,engine:c.engine,imageId:c.imageId},null,2));'
docker info
```

**预期结果：**显示候选版本、引擎和 `sha256:` 镜像编号；Docker 命令能显示 Server 信息。本机必须保留该编号对应的镜像。只有记录文件、没有实际镜像时，启动命令会失败；不要仅因标签名称相同就换用另一个镜像。

## 第 2 步：启动同一候选镜像

```sh
pnpm preview:release "$POLICY_CANDIDATE_REPORT" 8088
```

**预期结果：**终端显示体验地址、发布版本、引擎、记录目录、停止命令，以及 `READY_FOR_MANUAL_REVIEW（人工检查未评价）`。启动命令退出后容器继续运行，关闭终端或网页不会停止容器。

命令按镜像编号启动，核对镜像标签、CPU 架构、服务器返回的版本清单及其 SHA-256，并检查健康接口、版本跳转和浏览器隔离响应头。容器使用非 root 用户、只读文件系统、1 CPU/256 MiB，不挂载源码或本机目录，仅允许本机访问。

8088 已被其他服务占用时，将命令最后的端口改成 `8089` 等空闲端口。命令不会停止或替换其他容器。同版本、同引擎、同端口的本工具体验容器存在时，先核对镜像和运行限制，再复用或启动它；每次执行均新建记录目录。

## 第 3 步：在浏览器逐项检查

打开命令输出的体验地址。展开“使用说明与版本信息”，核对页面版本和引擎与终端一致，记录浏览器名称及版本。先按下表检查内置虚构样例，再使用获准在当前设备处理的实际 PDF。

| 检查项 | 操作与通过依据 |
|---|---|
| P02 金额变化 | 点击“P02 金额变化”。核对 1315 的 `USD 100 → USD 2000` 可见；1760 的 `USD 1000` 未改，不应被认定为本次金额修改。 |
| 来源、搜索与导出 | 在 P02 点击变化卡，核对高亮位于实际编辑；搜索 `1315` 能回到原文；导出 JSON，核对变化及新旧来源记录。只看到卡片数量不足以通过。 |
| P01 相同文件 | 点击“P01 相同文件”，没有内容变化卡，也没有已记录的覆盖缺口或对应未决。 |
| E03 扫描图片 | 点击“E03 扫描图片”，明确提示图片文字尚未比较；不能把零张文字卡理解为文档无变化。 |
| 交换方向 | 重新加载 P02，点击“交换方向”后开始比较。变化方向为 `USD 2000 → USD 100`。 |
| 取消后重开 | 使用处理时间足够的获准样本，在仍处理中点击“取消”，确认终止后能重新比较。若任务结束过快而未能实际取消，记录为未评价，并说明原因。 |
| 关闭任务 | 点击“关闭任务”，文件选择、密码、搜索及文档显示清除；重新加载样例后可正常比较。 |

发现错误时记录实际输入、版本、双方页码、预期与实际现象，保存获准分享的截图或导出文件。既有复杂表格、对应和扫描覆盖限制见 [项目使用说明](../README.md#结果怎么看目前有哪些限制)及[分层验收记录](../reports/issue-17/README.md)。本表是发布前基本操作检查，业务样本验收另行记录。

## 第 4 步：保存人工检查结果

将终端输出的“记录目录”完整路径写入变量，打开其中的记录文件：

```sh
export POLICY_PREVIEW_RECORD_DIR="这里替换为终端输出的记录目录"
cat "$POLICY_PREVIEW_RECORD_DIR/preview.json"
cat "$POLICY_PREVIEW_RECORD_DIR/manual-review.json"
```

**预期结果：**目录包含两个文件：

- `preview.json`：自动核对的镜像、版本、运行限制及启动结果。`READY_FOR_MANUAL_REVIEW` 只表示可以开始人工检查。
- `manual-review.json`：人工检查记录，所有项目初始均为 `NOT_EVALUATED`（未评价），不会因服务启动或自动用例通过而改为人工通过。

用文本编辑器填写 `manual-review.json` 的 `reviewer`、`reviewedAt`、`browser`，并逐项填写 `status`、`observations` 和 `evidence`。`evidence` 填与该项有关的截图或导出文件路径；保留版本、镜像、清单哈希和候选记录字段，不用其他版本的证据替换。

状态只用以下值：`PASS`（操作实际执行且有证据符合预期）、`FAIL`（实际结果违背预期）、`NOT_EVALUATED`（未执行或证据不足）。总体 `status` 在全部检查项通过时填写 `PASS`；存在失败填写 `FAIL`；没有失败但仍有未评价项时保留 `NOT_EVALUATED`。实际业务文件和包含原文的截图/导出按其授权范围保存，不直接提交公共仓库。

**完成标志：**每项都有真实结果及必要证据。存在失败时先修复并创建新候选重新检查；未评价项保留具体原因，并按项目放行要求处理，不能改称通过。真实 OpenShift 与正式使用者验收仍单独登记。

## 第 5 步：停止或再次试用

本工具容器名称由版本、引擎和端口组成。使用终端或 `preview.json` 中给出的完整停止命令，例如：

```sh
docker stop policy-preview-r20261104-bc9105e-mupdf-8088
```

**预期结果：**命令输出该容器名称，体验地址不再提供服务。仅停止对应体验容器。

再次试用时重复第 2 步，命令会重新核对镜像并启动原容器，同时创建新的记录目录，保留前次记录。无需重新构建。

## 故障处理与证据范围

| 现象 | 处理 |
|---|---|
| 候选状态不是 PASS，或版本/哈希/镜像信息不完整 | 查看原自动检查失败原因，完成新候选检查；不要手工把失败改成通过。 |
| 本机没有候选镜像 | 在保留镜像的机器执行，或从批准的制品来源恢复相同镜像后重新检查。不要用当前源码重建后冒充旧镜像。 |
| 端口占用 | 使用其他空闲端口；保留已有服务。 |
| 已有同名容器身份或限制不一致 | 检查该容器来源，或选择另一空闲端口；命令不会替换它。 |
| 启动或身份核对失败 | 查看新记录目录的 `preview.json`，其状态为 `START_FAILED`；人工项仍为未评价。修复后重新执行并保留失败记录。 |

默认记录位于候选记录所在目录的 `manual-review/<时间>-<随机编号>/`。需要指定位置时设置 `POLICY_PREVIEW_REPORT_DIR`，该目录必须尚不存在，避免覆盖历史证据。

本流程能检查发布镜像及浏览器操作；本机 Docker 运行不证明 OpenShift 已部署，也不证明真实 Route、HTTPS、账号访问控制、平台分配用户、网络策略或重新调度有效。容器的 256 MiB 限制不包括浏览器内的 PDF 处理内存，不能据此宣称普通办公终端性能通过。OpenShift 阶段继续按 [部署指南](deployment.md)执行。
