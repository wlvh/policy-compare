## 资料与分工

先选 3—5 对实际旧/新文档，尽量覆盖不同模板或生成来源，并记录来源、旧新版配对及原文件 SHA-256。由业务审阅者从完整原文独立列出关键变化；运行程序的人记录结果，双方最后核对。若同一个人承担两项工作，也须先完成并保存人工清单，再打开程序结果。

使用前需明确文件获准用于本地应用的范围、是否允许进入开发代理上下文、保存位置和访问人。获准在本地浏览器比较，不自动代表获准由 Codex 读取，或上传 GitHub/CI。若仅允许业务人员本地使用，可由他们操作应用，提供获准分享的记录。原文、结果 JSON 和截图均按同一资料范围保管；记录表填妥后也可能含敏感内容。

填写 [单对文档记录模板](trial-record-template.zh-CN.md)，每对一份，保存到获准的仓库外目录。仓库中的模板保持为空白。另准备至少 3 对不同模板或来源的独立留出：人工预期先封存，开发者不提前查看，也不用来调规则。留出不足不阻止这批探索试用开始，但业务试点验收仍不通过。

## 每对文档的流程

1. **先做人工基准。** 完整审阅旧版与新版，记录金额、责任、条件、日期等关键变化，附所属章节、双方页码和可核对原文。标明重要性，不按程序卡片形式拆分。保存时间和清单哈希，之后发现需要纠正时增加有理由的修订，保留原件。
2. **固定运行条件。** 记录电脑、内存、系统、浏览器、显示尺度和使用版本。两引擎使用完全相同的 PDF 字节、profile 和可见范围；一次比较的两侧固定同一引擎。换版本时关闭旧任务并重新读入两份文件。
3. **记录程序输出。** 保存各引擎的任务状态、覆盖提示、获准保存的结果与截图。按业务事件核对，不要求卡片数量、文本项 ID 或 JSON 一致，也不把另一引擎的输出当答案。
4. **观察实际审阅。** 让审阅者按平常方式看结果，记录重要变化是否被注意到、是否能快速回到正确原文、是否理解未比较区域。系统有输出但人没看到，与系统根本没检出分开记录。低价值提示淹没重要变化时，保留具体场景、提示数量与花费时间。
5. **最后对照人工清单。** 逐项记录漏报、误报和定位；检查人工清单中没有、但程序提示的新变化。仅查看尚未比较的区域并不算程序检出；明确覆盖警告也不等于静默漏报，两者分别说明影响。

3—5 对样本按 A/B、B/A 交替顺序使用两版，减少固定先后顺序的影响。第二次阅读会记得答案：同一审阅者的二次耗时不能直接证明某引擎更快；人工先读再用工具的耗时也不能证明工具提升了效率。此轮耗时用于发现卡顿、定位困难和审阅负担；若要证明节省时间，另用未见过文档及分配顺序的对照。少量真实样本不计算有代表性的 p95，也不替代已有正式性能与目标设备验收。

## 如何形成结论

每对文档只给出有证据的三类反馈：漏报（尤其重要金额/责任）、误报、定位是否便于核对，并补记人是否注意到以及是否理解覆盖范围。不新造综合分数；少量样本的“没有发现”不写成总体零漏报率。

发现关键漏报、错误完整状态或误导定位，保存原输入、独立预期和原结果，暂停该场景的依赖性使用；按根因修复并添加最小回归。不同根因新建问题，不因发现真实文档的新问题自动重新打开已关闭 F1—F7。预期不迎合程序输出，全部变化和折叠计数继续保留。

每次修改绑定新产品 SHA。已经向开发者披露并用于修复的样本转为回归集；修复后用未调参留出复核，披露过的留出须补换。产品改变后的正式性能按原要求重新绑定版本，旧测量保留。只有文档/记录变化时，不重复执行完整性能测量。

完成 3—5 对后汇总每版的重要漏报清单、误报负担、定位困难和范围理解问题，再决定下一步产品改动和默认版本。现有 45 页受控性能差距约 0.20—0.27 秒，不单独决定选择；真实字体、编码、版式表现、维护与实际许可范围一起考虑。
