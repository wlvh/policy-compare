# 独立合成 PDF 试用包

本包由独立审查方在运行产品之前编写，用于让 Codex 对合并后的比较工具做一轮有界、可复现的真实 PDF 流程测试。共有 **17 对、34 份 PDF、36 页**：14 对当前能力检查，3 对能力边界观察。所有人名、记录、金额均为虚构，PDF 页脚已标注 TEST DATA ONLY。

基准代码：`33ec5ba4448a686d65490f15e7be8c32d30bd74c`，即 PR #9 的合并提交。该轮工程验收已结束；本包作为新的试用输入，不重开 #2、不改原有 32 对规则样本。作者预期不来自产品输出。本包交付时尚未运行项目比较，也没有宣称样本已通过。

## 真值与文件

- `cases/<编号>/before.pdf`、`after.pdf`：已经生成、固定哈希的实际输入。
- `cases/<编号>/changes.json`：预先登记的作者编辑，沿用原 Python 分诊格式。`category=Unclassified` 仅用于格式兼容，不表示业务重要性。
- `identity.json`：作者声明的表与身份列，用 changes 文件哈希绑定；产品不读它。
- `author-layout.json`：每个绘制文字的原文、页码、表、记录、列与坐标。页码从1开始；同时给出左下和左上坐标系，单位为PDF点。扫描样本保留作者绘制位置，但实际PDF没有文本层。
- `manifest.json`：场景、边界、人工核对要求与四份输入文件SHA-256。
- `artifact-checks.json`：物料检查结果，只证明PDF制作与作者内容一致，不是产品验收结果。
- `generate.py`：独立作者源文件，可重建样本；运行产品不需要重建。重建需Python及`requirements-generate.txt`所列依赖。

## 执行

在包含本目录的项目工作区运行。产品依赖使用仓库锁文件；不升级依赖，不修改源码以适配样本。

```bash
pnpm install --frozen-lockfile
pnpm install:pdfjs
pnpm install:mupdf

python3 validation/synthetic-review-20261030/run-pack.py \
  --repo "$PWD" \
  --out /tmp/policy-compare-synthetic-20261030-run1
```

环境沿用项目要求的Node24和pnpm10.12.1。输出目录必须尚不存在；已有目录请换一个新名字。默认依次运行两个引擎，必要时可加`--engine pdfjs`或`--engine mupdf`单独排查。

`compare-pair.mts` 只调用项目原有 `loadEngine → extractPdf → parseDoc → compare`，同时保存两侧完整提取文档与产品结果。它只收到PDF路径，**不会读取作者答案、身份声明或预期**。随后 runner 调用原 `scripts/renewal-triage.py`，不新增评分器。

每个样本×引擎保留：

```text
left.doc.json / right.doc.json
result.json
compare.stdout.log / compare.stderr.log
triage-summary.json / triage-events.json / triage.stderr.log
```

根目录 `run-summary.json` 保留实际代码SHA、工作区状态、输入哈希、命令、退出码、核心与引擎版本和原始分诊汇总。运行失败时保留已产生的文件和日志。

**runner退出0仅表示调用完成，其中允许产品partial；complete_for_scope也只表示处理状态。二者都不能写成业务验收通过。** `expectations` 必须结合原PDF、作者布局、实际提取和卡片来源另行核对。

## 交给 Codex 的工作范围

1. 先读取本说明、manifest、根AGENTS.md，记录实际被测提交。保持样本PDF、作者编辑、身份声明和预期固定。
2. 运行全部17对×两个引擎；缺依赖按项目锁文件安装。运行错误记录具体阻塞，不改成未评价或跳过后称全通过。
3. 对14对能力检查逐项核对原文变化、实际编辑、新旧来源、记录与列归属。自动分诊结果与人工检查分列。P05/P12尤其不能用分诊接受代替列或表范围核查。
4. 对P10/P11查看两引擎真实提取项：字体分片若被引擎合并，只能说明普通换行测试结果，不能声称覆盖了原内部片段反例。
5. E01/E02/E03单列观察。保留已声明未评价和不支持范围；扫描无OCR不自动变成新增开发任务，但覆盖状态的确定陈述仍须真实。
6. 浏览器至少打开P02、P05、P10、P12各一对，在两引擎界面查看变化卡和选中后的新旧高亮；E03两引擎查看覆盖提示。通过实际点击核对，不能只凭CLI JSON声称界面定位通过。可以使用现有页面与浏览器工具；旧renewal-browser-check.ts硬编码旧样本，不可直接换目录冒充新样本UI验收。
7. 提交一份简短结果表：样本、引擎、作者修改、自动分诊、人工结论、证据位置、审阅代价。结论使用“符合该项预期 / 已证实违约 / 证据不足”；不要捏造一个未经定义的总准确率。
8. 第一轮先报告发现。对确定错误给最小反例与根因范围，不自动扩展格式支持、修改预期、启动新一轮大重构。产品故障与测试包自身错误需区分；如确有物料错误，先指出具体冲突再版本化修订。

PDF端到端测试只能检查产品实际产生的输出。原来“伪造矛盾卡片”“复用同一来源”的评分器拒绝能力仍由既有正式回归证明，本包不冒充替代它们。本次合成样本也不等同真实客户文档试用、业务签收或指定设备性能验收。
