# 保单比对规则验证与验收说明

版本：规则验证集 v1；固定种子：20261026

本包用于验证保单 PDF 比对程序是否发现已知变化、是否对应正确、是否能定位原文，以及是否如实报告未完成的部分。测试文档全部是虚构样本，不包含真实保单或客户资料。

本轮产品优先级明确为：关键变化尽量不漏，结果有原文依据，浏览器运行流畅，开发者可以在个人电脑上完整调试。语言和部署平台服务于这些要求。

本次交付包含 32 对文档、64 份 PDF、共 130 页，以及生成器、独立样本构造检查器、标准答案、来源记录和页面预览。共有 29 个预期事件：26 个必须发现的事件、2 个图像区域覆盖不足事件、1 个重复键组事件（2026-10-29 修订：R16 重分页实际新增的页标题 `POLICY WORDING` 登记为 Added/Review 必检事件后，为 30 个预期事件、27 个必须发现的事件；PDF 不变）。重复键组允许身份对应不确定，但必须显示两侧金额差异与原文证据。另有 6 对不应产生业务变化的控制用例。

## 0 基线的准确含义

基线是字体排版使用的一条参考线。水平拉丁文字中，H、n、x 的主体下缘通常靠近这条线；g、p、y 的下伸部分会越过它。因此，“字母站着”只是一个不够准确的比喻，不是所有字母的最低点都落在同一高度。

字符外框与基线是两类信息：外框用于标出文字所在区域；基线与书写方向帮助判断字符怎样组成一行。旋转文字的基线也会随之旋转，不能把所有文字都当成水平排版。精确高亮仍需要字符的四边形位置，不能只靠基线或整段外框推算。

## 1 样本的标准答案怎样产生

生成器先建立一份结构化的虚构保单，然后应用明确规则，例如改变同一字段的金额、删除否定词、移动条款、修改某一行的约定价值，最后分别生成修改前和修改后的 PDF。

标准答案来自源数据与变换记录，不调用被测比对程序生成。`source.json`、`expected.json` 和布局记录属于评估材料；产品实际测试输入是两份 PDF。不能把答案中的主体 ID、字段路径或事件列表作为额外输入传给产品，再宣称产品识别出了这些内容。

每个事件需要知道：改了哪个实体和字段，原值是什么，新值是什么，是否必须发现，是否必须默认可见，以及有哪些可接受的显示方式。位置记录还帮助审阅人员核对高亮是否落在正确页面和原文上。

## 2 分开衡量发现与对应

不要用“输出了多少条差异”代替质量评价。一个系统即使输出 50 条差异，也可能漏掉唯一重要的金额变化。

| 检查项 | 实际检查什么 |
| --- | --- |
| 变化发现 | 已知的金额、币种、措辞、期间等变化是否被指出。 |
| 对应正确 | 是否关联到正确主体、条款和表格行。 |
| 定位正确 | 左右证据是否落在正确页面与文字。 |
| 默认可见 | 关键变化是否被隐藏、误折叠或混入格式组而不易发现。 |
| 完整性 | 无法比较的页面或区域是否明确显示。 |
| 无意义告警 | 内容不变时是否凭空生成业务变化，或把纯重分页报成移动。 |

同一字段的修改显示为“删除旧值 + 新增新值”，可以说明变化被看到了，但对应质量仍可不合格。验收报告应分别记录，不能只打一个总分。

## 3 本轮的敏感度要求

本套样本默认所有需要发现的文字变化都应可见，`may_fold=false`。正常续期、标签变动也应先明确列出，不因为类别名称就自动收起。

对于实际产品，已确认仅为排版形式的变化以后可以按规则合并或折叠，并保留数量、理由和展开入口；金额、币种、期限长度、否定词、责任范围与不确定对应不得因此隐藏。

宁可保留有原文依据的增删或待复核，也不要强行把两个相似但不同的主体/条款配成一项。降低匹配阈值不等于提高发现率：过度强配反而可能把重要变化放到错误实体下，甚至被后续规则吞掉。

重复页眉优先合并相同变化的出现位置，让一项变化带多个定位入口。不要通过不计算页眉来换取清爽界面。告警太多也会影响人工审阅，因此应改善分组、排序和证据展示，而不是静默删除未确认内容。

## 4 发布门槛

以下门槛用于声明支持范围内、已经明确定义预期的验证集：

- 关键事件漏报数为 0。
- 关键事件默认被隐藏或误折叠数为 0。
- 未完成却显示“已完成、无差异”的次数为 0。
- 将不同主体或不同表格实体错误确定为同一对象的次数为 0。
- 每个必须发现的事件均能回到原文证据；几何精度不足时明确说明。

这些是有限验证集的发布条件，不是对任意真实 PDF 都保证零漏报。新发现的真实失败样本应脱敏后纳入回归。

## 5 特殊用例怎样判定

### 同内容重排版

同一 PDF 自比对不应有内容差异。受控重导出、字体或分页改变，要求业务变化为零；确有字符格式变化可以显示相应类别。不要把“没有业务变化”误写成所有差异类别都必须为零。

### 仅有图片的正文

无 OCR 的首版不能被要求读出图片里的金额变化。此类样本检查的是系统是否发现已知未覆盖的扫描页或区域，是否显示 `partial` 并定位缺口。

“已提示未覆盖”与“已识别图像中的金额变化”必须分开计数。扫描页只有页码被提取出来时，仍不能声称正文已经覆盖。

### 表格键重复

如果两行使用同一个键且无法可靠消歧，允许返回待复核或未完成对应。禁止仅按行号或先后顺序伪造确定的实体身份。

身份不确定不能成为隐藏已提取文字的理由。R25 要求显示重复键组两侧的金额内容或未配对差异，并提供两侧页面与文字来源。只显示“行键重复”不能算通过，也不能被计作已经识别了金额变化。

### 移动与重新分页

条款相对顺序或所属结构改变，可以形成移动。只因换页、页号或 y 坐标改变，不应产生业务移动。移动内部的一词修改仍须被发现。

## 6 这套规则集能覆盖哪些风险

规则样本适合检验明确的程序行为：小数点丢失、否定词变化、同名字段串主体、移动证据被替换抢占、表格行错配、页眉重要数字被过滤、重排版制造假变化、混合 PDF 被错误宣称完整。

它不能替代真实经纪人 PDF。真实文件可能有不同编码、字体、历史 OCR 层、复杂模板和不规范内容流，ReportLab 生成的文档往往更干净。

应继续保留少量真实文档的完整人工审阅和未调参留出集。改变 seed 能产生同一规则的新数值样本，但不能把这称为全新的、独立分布的留出验证。更有效的留出应含未见过的版式、规则组合和真实提取噪声。

## 7 生成检查与产品检查的区别

`fixture_checks.py` 检查样本是否生成正确，例如 PDF 是否可读、页数是否符合设计、关键文字是否出现、图像用例是否确实包含图片对象，以及预期记录是否能追溯到变换。

通过这些检查只表示样本与规则一致，不表示保单比对产品通过验收。本包没有接入产品比对引擎；接入后需要按第 2 至 5 节评估实际结果。

PDF 样本已进行页面渲染检查，布局记录为合成渲染来源证据。它不能代替检查产品从 PDF 中独立提取出来的字符几何。

在解压后的项目目录运行：

```bash
python -m pip install -r requirements.txt
python generator.py
python fixture_checks.py
```

生成另一批同规则的数值变体：

```bash
python generator.py --seed 20261027 --output dataset-seed-20261027
python fixture_checks.py --dataset dataset-seed-20261027
```

需要 Python 3.10 或以上版本。依赖版本与字体已记录；不同依赖版本可能使 PDF 字节发生变化，而逻辑测试仍相同。产品接入时需要一个小型结果适配器，把实际差异输出对应到这些独立预期事件。

## 8 浏览器性能另设验收

功能样本主要用于定位正确性问题，不用于证明长文档性能。浏览器性能应在实际使用的办公设备和浏览器上，记录以下环节：读取与初始化、提取、数据整理/传递、对应与差异、首次可审阅、页面渲染与搜索、峰值内存、取消和再次运行。

固定若干代表性文档，分别记录冷启动和热运行、页面数和字符量。真实长文档与模板大改导致的候选增多都要覆盖。Node 的耗时可以用于开发定位，不能替代浏览器的最终验收。

先维护一套正式核心。界面、配置和适配器可用 TypeScript，计算核心可以继续采用 Rust/WASM；选择以全流程实测为准。Worker 让重计算不阻塞界面，但不自动缩短总耗时。大字符数据要避免在 JS、Worker 和 WASM 之间反复整份复制。

MuPDF.js 自身已经是 WASM 引擎。TS 与 Rust 的选择主要影响后续结构化与比较等环节；不能假定更换核心语言就能改善提取、渲染或所有内存开销。页面按需渲染、缓存设置上限、显式释放 MuPDF 对象，以及限制候选组合，均需纳入原型。达到资源或计算上限时应如实返回未完成，不能输出“无差异”。

本次包尚未运行任何浏览器性能基准。建议先规定目标办公机、受支持浏览器、代表性短/长文档和候选大量增加的样本，再为首个可审阅结果、完成时间、交互响应、取消时间和峰值内存设定预算。用固定样本的分位数验收，不用一次最快结果代替性能结论。

## 9 本地调试与服务器部署

本地调试是硬要求：开发者应能在个人电脑上启动界面、提取器、核心以及需要的后端入口，用同一对 PDF 复现问题。

浏览器计算和后端计算都可以在 localhost 调试。生产若需要后端，默认交付与集群架构匹配的 Linux 容器；已有 OpenShift 环境申请应用配额和入口即可，不需要为本工具另建一个平台。

Harness 用于自动化发布，OpenShift 用于运行和管理容器。它们不应成为日常开发必须在线依赖的服务。生产接入前，再验证非 root 运行、可写临时目录、资源上限、身份隔离、文件清理和回滚。

| 选择 | 建议 |
| --- | --- |
| 开发机 | Windows、macOS、Linux 均可；用本地 HTTP 开发服务与 CLI 调试。 |
| 浏览器处理 PDF | 静态服务器只负责交付应用资源，计算与文档内存在用户电脑。 |
| 后端处理 PDF | 本机可先启动 Node 后端；生产交付 Linux 容器，继续复用相同提取器与核心。 |
| 初始后端压测资源 | 每个 worker 先按 2 vCPU、4 GiB、同一时间一对文档准备；这是待验证预算，不是实测最低配置或集群规格。 |
| 公司已有 OpenShift | 申请项目/命名空间、CPU/内存/临时存储配额、镜像仓库、域名/TLS、登录与发布权限。 |

生产后端要隔离每个用户的上传、任务和结果；解析放在受限进程或容器中，设置文件、页数、内存、执行时间和临时空间上限；取消必须停止计算；异常和资源不足应明确失败；任务完成后按约定清理文件，日志默认不记保单全文。容器应适应平台分配的非 root UID，使用明确可写的临时目录与非特权端口。

Harness 可以接公司已有构建流程，再将指定版本的容器镜像和部署配置发布到 OpenShift。OpenShift 负责实际运行容器和管理入口、资源、重启等。开发者不需要每改一行代码就部署，也不需要在本机先搭一整套 OpenShift。

## 10 使用前与上线前的边界

MuPDF 使用范围按原 T0 审查；本样本生成器使用 ReportLab、pypdf 和 Pillow，不依赖 MuPDF。字体许可随包附带，开发依赖仍需纳入组织实际要求的依赖清单。

真实保单的使用、存储和脱敏权限要在使用真实文件前确认；远端上传或 OCR/LLM 外传要在引入相应路径前确认。公司依赖仓库、登录入口和平台配额可并行办理，不应把所有事项都变成阻止合成样本和核心开发的前置审批。

| 时点 | 需要确认的边界 |
| --- | --- |
| 接入相关依赖前 | MuPDF 的许可方案、整体分发与服务方式、开发和生产范围；保留依赖和字体许可清单。 |
| 使用真实样本前 | 谁授权使用、能否带入开发环境、保存在哪里、谁能访问、是否需脱敏。 |
| 引入远端处理前 | PDF、提取后的全文 DocInput、OCR 或 LLM 请求允许发往哪些环境。DocInput 仍可能包含保单敏感信息。 |
| 接入组织环境时 | 依赖仓库、镜像仓库、单点登录、域名、网络出口和运行配额。 |
| 试点发布前 | 支持范围、未覆盖提示、用户隔离、资源上限、清理策略、依赖版本和回滚路径。 |

这些事项是否需要正式审批取决于组织实际规定。本说明不把组织未知政策当成已存在的强制流程。当前的虚构样本与不依赖 MuPDF 的独立开发可继续进行。
